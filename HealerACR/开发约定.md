# HealerACR 开发约定

这份文档是**踩坑记录**，不是设计文档。每一条都对应一个真实发生过的 bug，
加新技能 / 改逻辑前过一遍，能省掉大量"改了但没用"的来回。

---

## 一、七类已发生的 bug 模式

### ① 写死技能 ID，忽略 action change

**症状**：技能一直点但放不出来（游戏拒绝），或者干脆不放。

**原因**：FF14 里很多技能是"同一个技能位的形态"，会随 buff / 等级 / 状态替换。
硬放原 ID 会被游戏拒绝。

**已确认的清单**：

| 职业 | 基础形态 | 会变成 |
|---|---|---|
| 白魔 | 闪灼 | 闪飒（神速咏唱期间） |
| 占星 | 星极抽卡 | 灵极抽卡（互相替换，共享 55s CD） |
| 占星 | 出卡 I/II/III | 战争神之枪 / 世界树之干 / 河流神之瓶 |
| 占星 | 小奥秘卡 | 王冠之贵妇 / 王冠之领主 |
| 占星 | 占卜 | 神谕（92 级后） |
| 贤者 | 诊断 / 预后 / 注药 | 均衡诊断 / 均衡预后 / 均衡注药 |

**怎么认**：游戏里看技能说明，只要有
**「满足发动条件后，X 变为 Y」** 或 **「※该技能无法设置到热键栏」**，就是 action change。

**怎么写**：
```csharp
// 释放时一律走当前形态
var spell = SpellUtil.当前形态(技能);
if (spell == null || !spell.IsReadyWithCanCast()) return -1;
slot.Add(spell);
```

### ② 技能 ID 不在内置表里 → 静默失效

`SpellIds.取("闪飒")` 如果表里没有，返回 0 → `已解锁(0)` 恒为 false → 永远不放，
**而且不报错**。

**检查方法**：把代码里所有 `SpellIds.取("X")` 和表里的键做差集，必须为空。

### ③ buff ID 按等级段变化

DoT 每升一级就换 buff：占星 烧灼838 → 炽灼843 → 焚灼1881。
只检查一个的话，满级会一直认为"没上 DoT"，然后**无限补 DoT**。

**怎么写**：`JobSpellTable.所有DotBuff` 把所有档都列出来，查任意一个命中就算已有。

同类：贤者心关 2604 / 2871，白魔闪飒预备 3879 / 4326。

### ④ QT 开关被误判成 false

`HealQt.GetQt` 曾经直接返回窗口值、**兜底参数完全没用上**。
窗口里没登记的开关会返回 false → `Check()` 第一行就返回 → 技能逻辑一行都不执行。

**现在的规则**：
- `注册默认值` 时自己负责登记进窗口
- 只有**登记成功**的开关才信窗口的值（用户手动开关依然有效）
- 登记失败的退回默认值，**绝不误判成 false**

### ⑤ 木桩模式一刀切

`if (木桩模式) return -300` 会把"资源循环"和"练循环用"的技能一起拦掉。

**分类原则**：

| 类别 | 木桩该不该放 | 例子 |
|---|---|---|
| 纯治疗 / 减伤 / 召唤 | ❌ 拦 | 单奶、群奶、盾、减伤、复活、小仙女 |
| 资源循环 | ✅ 放 | 百合、蛇胆、以太、抽卡、花牌 |
| 输出 / 团辅 / 练循环 | ✅ 放 | 法令、神速、闪飒、地星、光速、天宫图、占卜 |

**注意顺序**：溢出类判断（百合满 3、蛇胆满 3）要放在**所有开关和木桩判断之前** ——
它是"止损"，不是"治疗"。

### ⑥ 有充能的技能会一口气全交

**四奶里 PvE 有充能的只有 5 个**（其余带充能的是 PvP，等级=0）：

| 技能 | ID | 充能 |
|---|---|---|
| 占星光速 | 3606 | 2 |
| 学者慰藉 | 16546 | 2 |
| 白魔无中生有 | 7430 | 2 |
| 贤者发炎 / II / III | 24289 等 | 2 |

**怎么写**：buff 检查 + 时间限流都要放在**所有条件分支之前**：
```csharp
if (已有这个 buff) return -3;                        // 已经在状态里
if (TimeHelper.Now() - 上次使用 < 3000) return -7;   // 刚按过
// 然后才是木桩 / 掉血等分支
```

### ⑦ 加了不该加的前置条件

**症状**：技能逻辑没问题，但"从来没轮到它"。

**已发生的**：
- 王冠之领主（自身周围 AOE）检查了 `当前目标() == null`
- 占卜（自身中心团辅）检查了 `当前目标() == null`
- 法令（自身中心范围）检查了 `当前目标() == null`
- 神速咏唱（自身 buff）检查了 `当前目标() == null`

**判断方法**：看技能说明的**范围/目标**描述。
写「对自身周围」「以自身为中心」「自身」的，**都不需要选中目标**。

## 二、加新技能的 checklist

1. **查 ID**：从 `dump_actions.tsv` 里找（工具在 `tools/SpellDump`），确认写进 `SpellIds` 表
2. **看技能说明**：有没有「满足发动条件后…变为…」→ 有就用 `当前形态`
3. **看充能**：`dump_actions.tsv` 的 `Charges` 列 > 1 → 加 buff 检查 + 限流
4. **看目标**：「对自身周围 / 以自身为中心 / 自身」→ **不要**写目标检查
5. **看木桩分类**：纯治疗拦、资源循环和输出放
6. **看资源**：会不会溢出？溢出要"无视开关"优先卸

---

## 三、排查技能不放的顺序

**别从技能逻辑开始查，先看输入条件**（这条是血泪）：

1. **QT 开关是不是 true** —— 加一行状态快照就能看到
2. **技能 ID 查得到吗** —— `SpellIds.取` 有没有报"不在内置技能表里"
3. **`已解锁` / `可用` 是不是 false**
4. **木桩/目标等前置条件**
5. 最后才怀疑技能逻辑本身

`AST_CrownPlay.快照()` 就是照这个顺序打的（每 5 秒一次，放在 `Check()` 第一行）。

## 四、日志约定

- 会每帧调用的地方（`Check()`、`SpellIds.取`），报错**必须去重**，否则日志会被刷爆
- 诊断信息用 `LogHelper.Info`，错误用 `LogHelper.Error`
- 临时诊断（如占星快照）确认没问题后可以降频或去掉

### ③ 补充：查档位要"从数据反查"，不要凭印象列

**0.3.5 的教训**：我给 DoT 加了三档就以为完事了，结果从 Status 表一查，
**四个职业每个都还漏了一档**：

| 职业 | 我以为齐了 | 实际还有 |
|---|---|---|
| 白魔 | 1871 天辉 / 144 烈风 / 143 疾风 | **2035 天辉** |
| 学者 | 1895 蛊毒法 / 189 猛毒菌 / 179 毒菌 | **2039、3089 蛊毒法** |
| 占星 | 1881 焚灼 / 843 炽灼 / 838 烧灼 | **2041 焚灼** |
| 贤者 | 2616/2615/2614 | **2864、3108、3976** |

而更早的"回归检查"之所以没抓到，是因为我扫的是**自己记得的名字**
（均衡 / 心关 / 闪飒预备）—— **凭印象列检查项，本身就是漏洞**。

**正确查法**：直接拿关键词去 Status 表里捞，同名条目**全部**列出来：
```powershell
Get-Content dump_status.tsv | Select-String -Pattern '天辉|烈风|疾风'
```

**推广到所有"按名字查状态"的地方**（DoT、姿态、预备 buff）：
一律先反查同名条目，再决定配几个 id。

**另外**：如果一个技能是**独立实现**的（比如 `SGE_Dot` 没走通用 `Res_Dot`），
那么给通用实现打的补丁它**吃不到** —— 改通用逻辑时，记得搜一遍有没有平行实现。

### ⑧ 断章取义地引用文档

**症状**：改动"看起来更有依据了"（引用了官方文档），实际上**依据被断章取义**。
比"凭感觉改"更危险 —— 因为它自带一层可信度伪装。

**实例**：技能可用性判断，我在同一个地方翻车两次。

**文档原文**：

> 技能是否可用 **IsReady**
>
> 注意，考虑到 Buff 延迟，**部分有 Buff 才亮的技能**，可能需要你自行比对本地有没有
> 释放获取 Buff 的技能。**此时**你可以通过 IsUnlock 检查是否学习/等级够不够，
> 接着使用 `xxx.GetSpell().Cooldown` 来检测技能 CD，再检测本地有没有释放过获取
> 对应 Buff 的技能

**我漏掉的两个限定词**：

| 限定词 | 作用 |
|---|---|
| 「**部分有 Buff 才亮的技能**」 | 限定**适用范围** —— 不是所有技能 |
| 「**此时**」 | 限定**触发条件** —— 只在上面那种情况才用 |

**于是我把"针对特定场景的补救手段"，当成了"通用的替代方案"**：

| 版本 | 我的改动 | 后果 |
|---|---|---|
| 0.5.5 | 只用 `IsReadyWithCanCast()` | ✅ 主判断正确（日志有 `CastSpell success: 17215`） |
| 0.6.7 | 换成 `s.Cooldown > TimeSpan.Zero` | ❌ 语义没验证，恒真 → **所有技能不可用** |
| 0.7.3 | 加 `!s.IsUnlock()` | ❌ 对召唤技/爆发技返回 false → **这两个不放** |
| 0.7.6 | 还原 `IsReadyWithCanCast()` | ✅ 回到实测可用的版本 |

**防范措施**：

1. **引用文档改动核心逻辑前，把整段原文（含限定词）贴进代码注释**
2. **再问一遍：这段的"适用条件"是什么？**
3. **文档建议 vs 实测数据** —— 实测优先。0.5.5 的日志已经证明 `IsReadyWithCanCast()`
   能把召唤技放出去，我不该因为文档提了别的 API 就把它换掉
4. **没有验证手段时不要改核心判断** —— 正确做法是先加日志**验证** API 的实际返回值，
   确认了再改；而不是"改了看会不会出问题"（那是拿使用者当测试机）

**同类风险点**：任何"文档/逆向里看到某个 API 就换上去"的改动。
**判断标准**：能不能说清这个 API 在**当前上下文**里返回什么、为什么它比我原来用的更好。
说不清就别改。

## 发版前自查清单

这份清单来自**两个官方文档的错误条目** + 本项目实际踩过的坑。
每次打包前对着跑一遍，**能挡掉大部分低级错误**。

### A. 错题集五条（AEAssist 官方《ACR开发错题集》）

| # | 错误 | 自查方法 | 正确做法 |
|---|---|---|---|
| 1 | **`OnNoTarget`/`OnPreCombat` 同步刷屏** | 看这两个方法体 | 空实现 `Task.CompletedTask`，或用 `Cast()` 扩展 |
| 2 | **技能 ID 演变**（居合术式） | 搜 `当前形态(` | 一律走 `MemApiSpell.CheckActionChange` 包装 |
| 3 | **目标为空底层拒绝使用** | 搜 `new Spell(` 带变量的 | 传目标前必须判空，null 就退回自己 |
| 4 | **能力技返回 0 但不打** | 看关键能力技在哪个队列 | 放 `Always` 队列；或检查 GCD 窗口 / `CurrGcdAbilityCount` |
| 5 | **Update/UI 里做 IO** | 搜 `File.` `Directory.` | 不在战斗中读写文件 |

### B. 开发文档三条（AEAssist3.0 ACR 开发）

| # | 要点 | 自查方法 |
|---|---|---|
| 6 | **Buff 延迟 → 主判断用 `IsReady`** | `可用()` 必须是 `IsReadyWithCanCast()`，**不要**换成 `Cooldown` / `IsUnlock` |
| 7 | **QT 战斗后重置要自行处理** | `OnResetBattle` 里要调 `HealQt.Reset()` |
| 8 | **技能/Buff ID 要可靠** | 硬编码表（Lumina dump 核对），不要指望 `MemApiSpell.GetId` |

### C. 本项目的额外清单

| # | 项目 | 原因 |
|---|---|---|
| 9 | **技能 ID ≠ buff ID** | 12 组不一致（再生 137/158、鼓舞 185/297、转化 3587/791…）→ 走 `AuraIds.技能转Buff` |
| 10 | **DoT 用剩余时间判断** | `HasMyAuraWithTimeleft(buff, 3)`，不是 `HasAura` |
| 11 | **充能技要看层数** | `GetCharges(id)`，满层缩短限流防溢出 |
| 12 | **AOE 用最佳落点判断** | `GetMostCanTargetObjects(id, N)`，不是数当前目标邻居 |
| 13 | **AOE 范围按职业** | 白魔神圣 8 米，其余 5 米 |

### D. **改代码时的操作纪律**（血泪）

> **这一节比上面所有条目都重要** —— 本项目一半的 bug 是我自己改出来的，不是逻辑写错。

| 纪律 | 为什么 |
|---|---|
| **① `Replace` 前先 `Select-String` 数命中处** | 我三次栽在这：`catch` 里被替换成无限递归、诊断代码被插入两处、方法被加到错误的类 |
| **② 替换 FAIL 就停下来看实际内容** | 有一次替换失败我还是打包了，发出去一个"以为修好了"的包 |
| **③ 编译失败绝不打包** | 有一次删代码删多了（漏掉闭合括号），58 个错误 |
| **④ 验证只看非注释行** | 注释里的字符串会造成假阳性（连中过两次） |
| **⑤ 打包后复查源码** | 确认改动真的落进文件了，不是"以为改了" |

### E. 关于 API 的使用原则（三轮翻车的总结）

**同一个地方翻车三次**（`Spell.Cooldown` → `Spell.IsUnlock()` → `GCDHelper.CanUseGCD()`），共同点都是：

> **看到一个 API 就换上去，没验证它的语义。**

**原则**：
1. **语义没吃透的 API 不用**（尤其别拿它当判断依据）
2. **文档建议 ≠ 必须改** —— 文档说的是通用情况，我有实测数据时**实测优先**
3. **没有验证手段时先加日志**，不要"改了看会不会出问题"（那是拿使用者当测试机）
4. **改动核心判断前，把文档原文（含限定词）贴进注释** —— 防止断章取义
