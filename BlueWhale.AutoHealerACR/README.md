# BlueWhale.AutoHealerACR

**一个实验性项目：让 AI（DeepSeek）尝试接管治疗 ACR 的技能判断。**

和 `HealerACR` 是**并列的独立项目** —— `HealerACR` 保持稳定可用，这个项目专门做 AI 接管这条线。

---

## 现状（v0.1.0）

**已完成**：
- 项目骨架（可编译成 dll）
- `AiSettings` —— API Key / 模型 / 开关，**存本地 json**
- `DeepSeekClient` —— HTTP 调用 + 超时 + **熔断降级**
- `AiStrategyLayer` —— **阶段 A：策略层**（异步、不阻塞战斗）

**未完成**：
- 阶段 B：决策层（AI 高频出技能建议）
- 和 `HealerACR` 的技能逻辑对接
- 设置界面

## 设计原则

### 1. AI 失败绝不影响战斗

```
API 挂了 / 超时 / 返回垃圾
    → 保持上一次的结论不变
    → 连续失败 N 次后熔断 M 秒
    → 期间全部走原有逻辑
```

**网络抖一下不能让 ACR 停摆** —— 这是整个设计的前提。

### 2. 延迟敏感度决定架构

```
FF14 GCD = 2.5 秒
DeepSeek 延迟 ≈ 1~3 秒
```

| 阶段 | AI 做什么 | 延迟要求 | 刷新频率 |
|---|---|---|---|
| **A. 策略层** | 调阈值、切优先级（"这波该攒还是该卸"） | 宽松，几秒都行 | 10 秒 |
| **B. 决策层** | 出具体技能建议（"下一个 GCD 放什么"） | **严格 < 2.5s** | 1.5 秒预取 |

**所以先做 A** —— 它延迟不敏感，能把「API 调用 → 解析 → 降级」整条链路先跑通。

### 3. 异步，但不在战斗线程等网络

对照 鍚岀被 ACR 的 `IsFairyGaugeReduced` —— 它也用 `AsyncVoidMethodBuilder` 做异步状态检测。
**共识：别在战斗回调里做同步 IO**（这也是官方错题集第 5 条的警告）。

## 配置

设置文件（和 dll 同目录）：

```
BlueWhale.AutoHealerACR.settings.json
```

```json
{
  "ApiKey": "sk-你的key",
  "Endpoint": "https://api.deepseek.com/chat/completions",
  "Model": "deepseek-chat",
  "超时毫秒": 3000,
  "启用策略层": true,
  "策略刷新秒": 10,
  "启用决策层": false,
  "决策预取毫秒": 1500,
  "连续失败上限": 3,
  "失败冷却秒": 60,
  "记录原始回复": false
}
```

**API Key 不进代码、不进发布包。**

## 阶段 A 的工作方式

```
每帧 → 到点了吗？（默认 10 秒）
         ↓ 是
      后台 Task 问 AI（不阻塞）
         ↓
      AI 回："保守|队伍血线普遍偏低且刚吃过全屏伤害"
         ↓
      解析成枚举 → 存下来
         ↓
      主循环读 当前倾向（永远瞬间返回）
```

**AI 给的是"倾向"，不是"具体技能"**：

| 倾向 | 含义 |
|---|---|
| **保守** | 保命优先：治疗阈值调高、资源留着救急 |
| **均衡** | 常规，按默认走 |
| **激进** | 输出优先：阈值调低、资源卸掉换伤害 |

## 为什么这个架构值得先试

1. **成本可控** —— 10 秒一次，一场副本几十次请求
2. **失败安全** —— 熔断后完全退回原有逻辑
3. **可观测** —— 每次策略切换都打日志，能看到 AI 在想什么
4. **为阶段 B 铺路** —— B 需要的「API 调用 + 解析 + 降级」这套东西，A 全做完了
